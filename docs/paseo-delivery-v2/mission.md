## Outcome and source of truth

Replace the planned local foreground/developer-mediated workflow with a portable TypeScript engine and CLI, Codex/Pi executors and a native Paseo dashboard. Existing local-mode plan/code is the behavior reference: its exact paths/hashes are in source-baseline.json. The legacy Python implementation was retired after replacement acceptance with explicit user authorization. Its last source version, including the preserved local-verifier test change, is available at Git commit `2d791bd`. No Python or Spec Kit subprocess implements V2 transitions.

Local mode means a trusted developer using their own workstation and existing selected `gh` login. No GitHub App setup, installation tokens, bot identity, OAuth, hosted service, or App-specific privileged publisher/container parity. Tasks run under deliberately selected provider permission modes. Worktrees protect edits; they are not advertised as a hostile-agent security sandbox. Optional local verification/isolation can use a repository's existing container profile, but Docker is not a universal prerequisite for starting local development.

The native repository panel replaces the local web dashboard and global Delivery sidebar entry as the preferred surface. `/delivery` opens or focuses the panel for the current Paseo workspace. The backend resolves that workspace to its canonical GitHub repository and coordinates related worktrees through one protected repository binding and runner. Only an explicit Start may dispatch work; opening, closing, refreshing, or switching the panel does not. The engine owns portable state, evidence, approvals and runner lifetime; the UI projects state and submits narrow local operator actions.

## Required behavior

1. A foreground CLI infers or explicitly selects the GitHub repository, reads trusted developer policy, serves status even when setup is incomplete, owns one foreground slot, and logs only meaningful sanitized state changes. Paseo can launch/observe it; it is not a new permanent service.
2. Auto-scheduling defaults off. A protected developer profile opts in per repository. Rank with complete issue/PR/dependency coverage; preserve ranking order while excluding locally serviced IDs. One active delivery per repository; filter/browse does not dispatch. Explicit requeue/start is needed to repeat completed work.
3. Plan and implementation remain candidate/revision bound. Persist skills/source/config pins, claims, attempts, checks, independent review and human review receipts. Correction invalidates stale evidence. Missing/rejected/stale evidence holds rather than advances.
4. Use one configured human GitHub account without changing the global active account. Scrub ambient token/host overrides; verify selected login, numeric actor and numeric repository identity before privileged operations. Tokens stay in trusted process memory or narrowly controlled Git authentication, never CLI args/state/dashboard/tasks/logs.
5. PR and issue publication each have independent off/explicit/automatic modes, default off. Explicit grants bind exact repository/actor/draft/content revision. Automatic mode requires trusted developer opt-in. No unsolicited issue generation. Queue issue proposals deliberately and retain a durable spool; PR handoffs derive from verified candidate records.
6. Allowed writes: candidate branch push, draft PR create/update, explicitly queued issue proposal create. Keep one bound draft across corrections and reconcile ambiguous responses before retry. Mark-ready, tracking labels, GitHub reviews and merge stay human actions; the runner observes/readbacks them. Deployment is separate explicit authority.
7. Poll fresh state with bounded verification retries and transient-read backoff, respecting server retry deadlines. Never automatically recover a stranded execution, synthesize a review receipt or guess remote success.
8. Ctrl-C stops new scheduling and drains owned in-flight work through a durable publication boundary; preserve unresolved execution/intent after forced loss. Resume revalidates identity/pins. Pause and cancel have explicit ownership and effect-disposition semantics.
9. Native workspace panel provides repository-scoped run selection, current stage/next action, exact candidate, PR/issue links, saved review versus confirmed progress, local/Actions verification and freshness, setup, runner lifecycle, errors/empty/disconnected/recovery states. Repeated `/delivery` focuses the existing panel. Closing it leaves explicitly started work running and reopening reconnects. Draft payloads remain private by default; show safe metadata. State export and CLI inspection work without Paseo.
10. Resolve the live workspace to canonical repository, Git root, common Git directory, branch and worktree. Related worktrees and clones share one binding, state root, active claim and repository runner. Process loss is distinct from pause, stop and completion; recovery is explicit, pin-bound and reconciles recorded external effects before another dispatch.

## Scope boundaries

- One implementation includes engine, local GitHub/Git publisher, queued proposals, foreground control, executor adapters, native dashboard and tests. No phased Python bridge.
- State lives in an explicit owner-controlled directory outside Paseo plugin data. A new versioned namespace refuses writable legacy state; existing runs remain inspectable with their existing executable. No automatic schema migration.
- No active daemon restart, credential/account change, remote issue/PR mutation, merge or deployment is authorized as part of local validation. The later user-authorized plugin enablement and read-only custom preview are recorded above; execution/control validation remains on a disposable test daemon, Git remotes and HTTP fixtures. Local code implements production GitHub operations, but live-write qualification is separate.
- Preserve original checkout dirty work and sibling worktrees. New source only under packages/delivery and plugins/paseo-delivery.
- Use Node/TypeScript with built-in APIs, plus required official Paseo plugin/SDK host modules. Avoid new general orchestration infrastructure.
